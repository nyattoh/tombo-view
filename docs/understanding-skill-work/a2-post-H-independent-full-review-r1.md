## 2. Severity-Ranked Actionable Findings (`file:line`)

### Finding 1 (Medium / High Impact on Host-Session Recovery) — `invalid_model_output` diagnostic message is swallowed when `maxModelRepairAttempts === 0`
- **Location**:
  - [`src/core.ts:537-553`](../../src/core.ts#L537-L553) ([`propose`](../../src/core.ts#L510-L555))
  - [`src/core.ts:622-624`](../../src/core.ts#L622-L624) ([`inspect`](../../src/core.ts#L604-L626)), [`src/core.ts:654-656`](../../src/core.ts#L654-L656) ([`update`](../../src/core.ts#L627-L657)), [`src/core.ts:686-688`](../../src/core.ts#L686-L688) ([`reflect`](../../src/core.ts#L658-L690))
  - [`skills/tombo-view/scripts/session.mjs:131-145`](../../skills/tombo-view/scripts/session.mjs#L131-L145) ([`run`](../../skills/tombo-view/scripts/session.mjs#L15-L214))
- **Reproduction / Evidence**:
  - [`session.mjs:133`](../../skills/tombo-view/scripts/session.mjs#L133) constructs `createTombo({ model: ..., journal })` without setting `maxModelRepairAttempts`, which defaults to `0` at [`src/core.ts:460`](../../src/core.ts#L460).
  - In [`propose`](../../src/core.ts#L537-L553), when `apply(current, proposal)` throws `TomboError('invalid_model_output', message)` (e.g., `"Resolution lacks current matching evidence priority-gap"` at [`src/core.ts:390`](../../src/core.ts#L390)), `current.modelRepairDiagnostics` is only populated inside `if (attempt < maxRepairs)` ([`src/core.ts:547-550`](../../src/core.ts#L547-L550)). With `maxRepairs === 0`, `lastError` is rethrown without recording any diagnostic.
  - [`inspect`](../../src/core.ts#L622-L624), [`update`](../../src/core.ts#L654-L656), and [`reflect`](../../src/core.ts#L686-L688) catch `TomboError('invalid_model_output')` and return `stop(next, 'invalid_model_output', ...)`, discarding `error.message`.
  - In [`a2-H01-A4-actual-user-r4-full-thread-trace-r1.json`](a2-H01-A4-actual-user-r4-full-thread-trace-r1.json) at **position 31** (stage 3) and **position 50** (user-r4), `session.mjs update` exited `1` with `stopReason: "invalid_model_output"` and `error: undefined`. At **position 52**, the Codex host agent had to run `Get-Content dist/core.js` (lines 65–101) to reverse-engineer why its proposal failed.
- **Consequence**:
  - When a multi-claim / multi-resolution `update` or `reflect` fails validation in a host session, the host agent receives zero feedback on *which* claim, assessment, or resolution violated the contract. In H01-A4 stage 3 (position 32), the agent guessed blindly and stripped *both* resolutions (including a valid `not_applicable` resolution on `preparation-gap`). In H01-A4 user-r4 (position 53), it stripped the `priority-gap` and `preparation-gap` resolutions, burning 2 of its 3 remaining `modelCalls` on blind recovery and hitting `budget_exhausted` (`12/12`) at `reflect`.
- **Narrow Actionable Design Recommendation (if runtime change is authorized)**:
  - Record the terminal `TomboError('invalid_model_output').message` in `state.modelRepairDiagnostics` even when `attempt === maxRepairs` in [`propose`](../../src/core.ts#L545-L553) (and surface the latest `modelRepairDiagnostics` message as `validationFeedback` in [`prepareRequest`](../../src/core.ts#L510-L535) when retrying from an `invalid_model_output` state).

### Finding 2 (Medium) — Rejected `tombo.update` commits `observations_recorded` before validating the proposal, locking in mismatched `evidence.scope` strings
- **Location**:
  - [`src/core.ts:631-656`](../../src/core.ts#L631-L656) ([`update`](../../src/core.ts#L627-L657))
  - [`src/core.ts:276-303`](../../src/core.ts#L276-L303) ([`mergeEvidence`](../../src/core.ts#L276-L288), [`mergeObservations`](../../src/core.ts#L290-L303))
  - [`skills/tombo-view/scripts/session-store.mjs:115-119`](../../skills/tombo-view/scripts/session-store.mjs#L115-L119) ([`assertObservationsMatchReceipts`](../../skills/tombo-view/scripts/session-store.mjs#L115-L119)) and [`381-393`](../../skills/tombo-view/scripts/session-store.mjs#L381-L393) ([`applyManagedOperation`](../../skills/tombo-view/scripts/session-store.mjs#L351-L397))
- **Reproduction / Evidence**:
  - In [`H01-A4-r4` position 49](a2-H01-A4-actual-user-r4-full-thread-trace-r1.json), the host agent bundled the user's priority and preparation answers into one evidence item `user-priority-and-limit` with `scope: "user priority and preparation limit for this reading meeting"`, whereas stage-1 claims `priority-small-groups` and `preparation-flexible` had scopes `"user priority for this reading meeting"` and `"user preparation capacity for this reading meeting"`.
  - When `session.mjs update` ran at **position 50** (`rev 10 -> rev 11`), [`tombo.update`](../../src/core.ts#L631-L638) committed `observations_recorded` (`rev 10`) *before* calling `propose()`. When `propose()` failed with `invalid_model_output`, `state.evidence` already contained `user-priority-and-limit` with the combined scope string, and `state.pendingAssessmentExecutionIds` contained `user-priority-and-limit-observed`.
  - Because [`mergeObservations`](../../src/core.ts#L293) enforces `stableJson(existing) === stableJson(observation)` for any already-recorded `executionId` and [`mergeEvidence`](../../src/core.ts#L279-L280) enforces immutable `existing.scope === incoming.scope`, the host agent could not edit `user-priority-and-limit.scope` in place on retry (**position 53**).
- **Consequence**:
  - Once a host agent records an observation whose `evidence.scope` differs from an earlier claim's `scope`, it cannot fix the evidence scope in place on retry; it must either attach additional scoped `EvidenceItem`s in a new observation or run `session.mjs invalidate` to discard the pending execution.
- **Narrow Actionable Design Recommendation**:
  - Document explicitly in [`skills/tombo-view/references/host-session.md`](../../skills/tombo-view/references/host-session.md#L107-L113) that if an observation was already recorded with a non-matching `evidence.scope`, its `scope` is immutable in `state.evidence`, so closing an older differently-scoped claim requires either `session.mjs invalidate --discard-execution <id>` or recording a distinct `EvidenceItem` whose `scope` matches the target `claim.scope`.

### Finding 3 (Low / Schema-Contract Sharp Edge) — `InformationGap` allows `claimIds: []` with `blocking: 'required_before_completion'`, creating gaps that can never be resolved as `supported` or `refuted`
- **Location**:
  - [`src/types.ts:44`](../../src/types.ts#L44) ([`InformationGap.claimIds`](../../src/types.ts#L40-L48))
  - [`src/core.ts:119-134`](../../src/core.ts#L119-L134) ([`resolutionValid`](../../src/core.ts#L119-L134))
  - [`src/core.ts:384-396`](../../src/core.ts#L384-L396) ([`applyUpdateProposal`](../../src/core.ts#L363-L402))
- **Reproduction / Evidence**:
  - [`resolutionValid`](../../src/core.ts#L122-L130) requires `gap.claimIds.length > 0` for both `reason === 'supported'` and `reason === 'refuted'`.
  - Meanwhile, [`InformationGapSchema`](../../src/core.ts#L151-L159) permits `claimIds: []` alongside `conditionRefs: ["task:goal"]` and `blocking: "required_before_completion"`, and [`applyUpdateProposal`](../../src/core.ts#L384-L386) forbids mutating an existing gap's `claimIds`.
  - In both `H01-A3` stage 3 and `H01-A4` stage 3, the Codex agent created `current-preparation-note-gap` during `reflect` with `claimIds: []` and `blocking: "required_before_completion"`. When it immediately tried to resolve `current-preparation-note-gap` as `supported` in the next `update`, [`resolutionValid`](../../src/core.ts#L123) rejected it, leaving `current-preparation-note-gap` permanently `open` (unless closed via `not_applicable`).
- **Consequence**:
  - Post-H [`skills/tombo-view/references/host-session.md:109-111`](../../skills/tombo-view/references/host-session.md#L109-L111) accurately explains this constraint in prose, but the SDK schema still permits creating a `required_before_completion` gap with `claimIds: []`.
