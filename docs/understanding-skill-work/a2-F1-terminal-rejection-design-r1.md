## Chosen additive contract (proposed names for reviewer confirmation)
1. Add createTombo option captureProposalRejection?: boolean, default false, validated boolean. Managed helper opts in explicitly; legacy helper/default SDK/CLI configuration remains unchanged. maxModelRepairAttempts retains default0 and existing0/1/2 behaviour. Enabling capture must not itself enable another attempt or model call. Initial inspect failure/return behaviour unchanged, including throw with zero repair; capture applies only update/reflect with an existing state.

2. Add optional state.lastProposalRejection, one object only (no new accumulating array). Proposed strict shape:
operation:'update'|'reflect'; taskId; atRevision; understandingHash; code:'invalid_model_output'; kind:'resolution_not_justified'|'reflection_binding_mismatch'|'reflection_claim_coverage_mismatch'|'proposal_validation_failed'; optional target:{kind:'gap'|'claim'|'probe'|'lens',id}; rejectedAttempt; maxAttempts.
Counts describe actual SDK attempt and configured automatic attempt count, not permission to retry externally. The record is created only on terminal invalid_model_output after an actual generation/apply attempt, not pre-generation invalid_input, budget, accounting, timeout or arbitrary adapter exception. It binds to the ACTUALLY RETURNED failed state (taskId, resulting revision, understandingHash), including validated observations retained there. It replaces the previous object on a later genuine terminal rejection; no inferred legacy backfill.

3. Safe origin/classification: do not store error.message, raw Zod issues, proposal fields/text, claim text, reasons, passages or arbitrary adapter exceptions. Use SDK-controlled validation provenance/guard mapping and static diagnostic kinds. Map the first recognised internal failing guard to an existing returned-state entity only; unknown/new-candidate/unregistered IDs yield generic category without a target. An adapter-thrown lookalike string must not impersonate an internal guard. Target identifiers must be bounded known protocol IDs; omit targets with controls/whitespace or unbounded/untrusted values. No semantic word blacklist, oracle, generic classifier or new evidence-validation rule. Reviewer must challenge the smallest safe way to convey provenance (internal typed error detail vs narrow internal guard handling) without duplicating SDK validation in helper.

4. ModelRepairDiagnostics and positive-repair compatibility: existing automatic repair diagnostics/feedback remain unchanged. This separate opt-in terminal record must not add repair iterations, replace legacy inspect exceptions, hide failed attempts or invent token/cost/round/tool usage. Successful update/reflect removes the current lastProposalRejection in the new state; prior immutable journal snapshots remain. Other operations/checkpoints need not rewrite old snapshots: a record which no longer matches revision/operation/hash/stop is inactive. SDK understandingHash remains unchanged solely by diagnostic metadata (explicit existing semantic fields); whole state journal/session digest normally includes the optional field.

5. Next managed prepare uses it only if current state.stopReason is invalid_model_output, taskId/revision/understandingHash match, operation matches, target if present still references the current state, exact pending batch checks pass, and current SDK/session deadline/accounting gates allow prepare. The same applicability logic governs preparing and validating the submitted envelope, so requestHash remains exact. A deterministic safe message derived from kind/known target and the real rejectedAttempt/maxAttempts populates existing request.validationFeedback. The typed record is already available in request.state; no new model schema requirement, mandatory proposal field or extra generation. If no applicable new record, preserve existing legacy modelRepairDiagnostics behaviour. Never pass old rejection as active feedback after success, other operation, different revision/understanding, budget/deadline stop or legacy replay missing the field. Expired status may show old record as history, never create a new request/evaluation.

6. Persistence and compatibility: SDK state schema/type adds only the optional record, schemaVersion remains0.1. Legacy journals/cache/redacted replay with no field load identically; no migration/backfill or rewriting old hashes. New failed state goes through existing managed begin/stage/commit/reconcile, no new session authority/event schema, no session-store edits unless independent design proves unavoidable. The SDK ledger owns the diagnostic along with the actual failure state. Restore/replay preserves the saved record as metadata without recreating a rejection or accounting it twice. Redaction must not copy private source strings into this metadata.

## Meaningful pre-product RED and invariants
Use actual helper subprocesses/public SDK, not unknown-flag-only failures or prose matching:
- Validly shaped update with an existing mismatched-scope/unsupported resolution: exactly one host adapter generation, real stopped invalid_model_output, rejected changes absent, validated observations/consumption retained, safe target diagnostic survives SDK/session/cache replay and a new-process prepare with correct binding.
- A reflected required gap with no claim target cannot be supported/refuted resolved: safe rejection diagnostic but gap stays open; no auto repair/downgrade.
- Correct same pending batch retry uses new actual model/round counts but no duplicate external tool/known expense; unchanged execution payload, evidence scope, partial-batch/new-observation mixing protections remain.

- Legacy/replayed/redacted states not backfilled; fresh diagnostics do not change semantic understandingHash/claim/gap/validity decisions, though normal whole-state digest/revision records the real operation.
