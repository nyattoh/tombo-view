# 状態更新と保存の分担

TOMBOのデータは、主張、証拠、未確認事項、検査、実行の記録を別に保持する。主張の確からしさと未確認事項の処理状態は別の軸である。生成アダプタは候補と証拠評価を提案し、コアが参照と条件を検証して状態を更新する。

公開APIは `createTombo({ adapter })` の `inspect`、`update`、`invalidate` とする。呼出し元は外部検査を実行し、観測を渡す。コアが外部ツールや提供者を選ばない。

保存は `FileJournal` が担当する。`expectedRevision` を排他区間で照合し、検証済みの状態スナップショットをJSONLへ追記して同期する。証拠本文は履歴から除去する。状態JSONのキャッシュが保存できなくても、確定した履歴から復元できる。

差分イベントのみの方式も検討したが、v0.1の小さな状態では完全な構造化スナップショットが復元規則を簡単にする。状態全体を返すモデル出力とは別であり、保存するのはコアが検証した状態である。

もう一つの案は、生成と保存を一つのセッションAPIへまとめる方式である。呼出し元の操作は減るが、メモリー内だけで使うSDKもファイルの寿命と競合規則へ依存する。v0.1ではコアと保存を分け、保存側だけに小さなクラスを使う。

同じ実行結果の配送は `executionId` で重複を除外する。実際の再実行には新しいIDを使う。証拠の原資料や本文の重複とは別に扱う。外部検査を実行済みなら、予算上限を超えていても実際の利用量を記録し、新しいモデル呼出しを停止する。

効果の比較実験と実プロバイダー接続は未実施である。固定の再生デモを未知の検出能力の証拠として扱わない。
